# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

A personal-use Foundry VTT v14 module that runs *The Quiet Year* inside an existing world. Plain JavaScript loaded as a classic script — no build step, no bundler, no package.json.

## Project rulings

- **No i18n.** User-facing strings stay hardcoded English. Do not add a `lang/` directory, `game.i18n.localize`/`format` calls, or localization keys, and do not flag their absence in review. This overrides the general FoundryVTT guidance (including the `foundryvtt-dev` plugin's skills) that all user-facing text must be localized.
- Personal-use helper, not a distributable product. Card text was transcribed from the author's copy of the game.

## The module id is load-bearing

`MODULE_ID` in `scripts/quiet-year.js`, the `id` in `module.json`, and the containing **directory name** must all be `quiet-year`. Foundry refuses to load a package whose id does not match its directory:

```
Invalid module "quiet-year-cobalt" detected in directory "quiet-year"
```

`MODULE_ID` also determines the settings namespace, the flags stamped on every document the installer creates, and the template path. Changing it orphans the settings and documents of any world that ran the old id.

## Running it

There is no test suite, linter, or build. Verify changes in a live Foundry:

```bash
node ~/Applications/foundry-14/main.js \
  --dataPath=/Users/timlwhite/FoundryVTT-Next --port=30001 --world=v14 --noupnp
```

Port 30000 is occupied by WebStorm's `cef_server`. The `v14` world is the scratch world and has exactly two users, `Gamemaster` and `Player`. `node --check scripts/quiet-year.js` is the only static check available.

Testing multi-client behaviour needs two real sessions — Foundry's session cookie is per browser profile, so two tabs in one profile are the *same* user. With the chrome-devtools MCP, `new_page` with distinct `isolatedContext` values gives two independent sessions in one browser.

**Gotcha when driving it headlessly:** a backgrounded tab has its animation frames paused, so Foundry does not flush that client's document writes until the tab is woken. Driving the GM in a background tab makes every update look like it arrives one action late. Keep the acting tab in front (`select_page` with `bringToFront`) before measuring anything.

## Architecture

Everything lives in `scripts/quiet-year.js`, in four parts: the `SEASONS` card data, the idempotent installer, the state model, and the play-surface ApplicationV2.

**Two sources of truth.** The play surface renders from both, and anything that keeps it current has to watch both:

1. The world setting `quiet-year.state` — season, current card, projects, abundances/scarcities (plain string arrays, edited as structured lists and addressed by position with the drawn value as a guard), contempt, game-over flag. Read through `getState()` (merged over `freshState()`, so missing keys are tolerated) and written only through `setState()`.

   A project carries a `status` of `active`, `completed` or `cancelled`. `mergeObject` replaces arrays wholesale rather than recursing into them, so projects saved before that field existed arrive still shaped `{ id, name, weeks, completed }` — read the status through `projectStatus()`, which falls back to the old boolean, and never test `project.status` or `project.completed` directly. Only `active` projects tick, and only they count towards the cards' "no projects underway" test; a cancelled one keeps the weeks it had left as the record of where it stood.
2. The four `Cards` decks' per-card `drawn` flags — the authority on which cards remain. `seasonRemaining()` derives the "N cards remain" count from these, not from module state, so card updates propagate as their own document events.

**Live sync across clients.** Every refresh funnels through the debounced `refreshPlaySurface()`, fed by three sources: the state setting's `onChange` (Foundry calls it on every client, covering both writes and the create on the first write in a fresh world), a `deleteSetting` hook (the one case `onChange` is not called for), and the `createCard`/`updateCard`/`deleteCard`/`updateCards` hooks filtered to the kit's own decks. `setState()` calls the same helper so local and remote paths behave identically, and the debounce collapses a draw's setting write plus card updates into one render. `registerRealtimeHooks()` is called from `ready` **before** the GM-only early return — players need it most.

**Uncommitted input survives re-renders — and so does anything else the local user put in the DOM.** Since a render can arrive at any moment from another client, the app tracks which fields the local user has typed into (`_dirtyFields`) and carries those values and the caret across the render, in `_preSyncPartState`/`_syncPartState`. Committing clears the flags so incoming state wins again, and any new field needs the same treatment.

Those two hooks are the right place because of *when* `HandlebarsApplicationMixin` calls them: it pre-syncs every part, replaces every part, then re-syncs, with nothing awaited in between, so nothing can be typed between the capture and the restore. A hook that awaits anything — `_prepareContext`, `_onRender` — would snapshot the form, yield to the event loop, and then restore stale values over whatever was typed in the gap. Core's own halves of those hooks already carry the focus, the scroll positions a part names in `scrollable`, and the open state of any `details[data-sync]`; call `super` and add to `state` rather than replacing them.

There is no save button left: project names, resource entries and player names commit through `commitOnBlur()` when they lose focus or take an Enter, and every other control writes outright. That helper deliberately does **not** use the `change` event — `_restoreDrafts` writes a surviving draft back with `el.value = …`, which resets what the element believes it held at the last change, so a value typed before a render from another client and blurred after it would fire no change event at all and be silently lost. It compares against `_renderedValues` instead. It also refuses to commit while `state` is `RENDERING`: swapping the part out fires `blur` on whatever was focused, and Chrome fires it with the element still connected, so there is no way to tell that blur apart by looking at the element. Committing on it would measure the draft against the baseline from *before* the render and write it straight back over the value that render was carrying — another client's rename, undone by a keystroke nobody finished. The draft is not lost by being skipped: `_preSyncPartState` already has it, and `_restoreDrafts` puts it back and leaves it dirty unless the incoming render disagrees with it. `RENDERING` is only ever set between `_renderHTML` and the swap, so a real blur cannot land in it, and closing the window tears the field out with the surface already `CLOSING` — the commit people rely on when they type a name and shut the window still happens. A write that declines to happen (a row that has gone, a name that already said that) must call `refreshPlaySurface()`, or the field keeps showing a value the world does not have.

State that is not a form field needs carrying too — the history's `<details>` open and its scroll position, which any other client's write would otherwise snap shut mid-read. Both are core's to keep: the disclosure because it is marked `data-sync="history"`, the scroll because `PARTS.surface.scrollable` names `.qyc-history-list`. Anything similar added later wants the same two markers before it wants code.

An action queued from a click must carry what it was aimed at rather than resolving it when it runs. `recordAction()` takes the week number from the button that was on screen: the queue can put a draw in front of it, and "the current week" by then is the next one — which would record the action against the wrong week and spend that week's allowance.

**Weeks are counted, not derived.** `state.week` advances in `drawWeek()` and `state.log` gains an entry per week — the card drawn and the actions taken against it. The count follows prompts resolved rather than cards marked drawn, because Summer's King discards two further cards that are not weeks of their own; that card instead sets the week's `allowance` to 2. A game saved before the counter existed is seeded once from the cards already drawn across all four decks (`migrateWeekNumber()`), which is an approximation — the true number is not recoverable — but better than sending an in-progress year back to week 1.

**Undo is a snapshot, not an inverse.** Draw Week and Tick Projects record what the tracker held before they ran, the cards they marked drawn and the chat message they posted, in an `undo` world setting of their own — kept out of `state` so a snapshot never captures the stack that preceded it. Neither operation can be inverted from its end state: Summer's King discards two cards chosen at random and leaves nothing saying which, and a tick only touches projects that were active with weeks left. A tick also records that the week's dice were adjusted, so it pushes an entry even when no die moved — see below.

**A snapshot covers only the fields its action writes** — `DRAW_FIELDS` for a draw, and for a tick a per-project patch of `TICK_PROJECT_FIELDS` on just the projects it counted down, addressed by id so a rename made since survives. It has to: the stack records two operations but every other path writes the same setting, so a full snapshot would make undo a rollback of the world rather than of the action, wiping a player's Contempt mark or a project finished early between the action and the click that takes it back. Undo merges the recorded fields over the current state rather than replacing it. An action that joins the stack brings its own field list.

**Order matters in `undoLast()`**: restore the state, then pop the stack, so a failed restore can be retried rather than stranding the year with its cards already returned. And an action pushes its entry *before* it posts its chat message, patching the id in afterwards with `attachUndoMessage()` — pushing after would mean a vetoed or failed message left the action applied with nothing to undo it.

**Serialized actions must not await each other.** `serialized()` puts an action's whole body in the shared write queue, so one calling another would wait for a turn that cannot come until it returns. Chain them from the caller instead — Add Project records the week's action with `.then(() => recordAction(…))`, not from inside the queued task.

**Everything is idempotent and flag-tagged.** The `ensureDeck`/`ensureJournal`/`ensureScene`/`ensureMacro` helpers find existing documents by `getFlag(MODULE_ID, …)` rather than by name, so `installKit()` doubles as the repair path and re-running it never duplicates.

What each helper reconciles on an existing document is a deliberate choice, and the create-only ones say why in a comment. `ensureMacro` reconciles name and command; `ensureDeck` reconciles ownership but never the cards, because rewriting them resets every `drawn` flag — the authority on which cards remain — and would hand a table mid-game a fresh deck. `ensureScene` reconciles nothing: the scene exists to be drawn on, and restoring its dimensions or grid would move a year of drawings. `ensureJournal` brings forward any page it can prove is still its own, in both journals; `{ reconcile: true }` decides what happens to a page it cannot vouch for. The rules journal is generated reference text, so an unrecognised page there is reported and a missing one replaced; the setup journal is a workbook the table writes in, so an unrecognised page there is simply left, and nothing is added to a journal that already has pages of its own — which is reported as `absent` rather than `kept`, because the kit's prompts and tables are then not in that world at all. Only a page name the kit gave is reconciled, never one the GM chose, and where two pages both carry the kit's flag (duplicating a page copies them) the one still holding what the kit wrote speaks for it.

**The game's text is not in this repository.** The card prompts and the rules summary are read at install time from `content/` inside the module directory — four `<season>.json` files and `rules.html` — which is gitignored except for its own README. What stays in the source is what the module invents: which suit is which season, the ranks a deck holds, the card document's shape, and `setupHtml`, which is original writing about sector-scale play rather than reproduced game text. `readContent()` caches per session, and treats a 404 as absence rather than failure, because someone who has not transcribed their copy yet is the expected case, not an error.

**Absence degrades, it never fails.** A deck with no content file is still created with all thirteen cards in rank order, carrying no prompt; the content files hold plain text, so it is escaped on the way into the card's HTML. A malformed or incomplete file says which file and what is wrong with it — an unknown rank, a duplicate, a missing prompt — and fills in what it can. `installKit()` reports every missing file once, up front, rather than once per step.

**The rules journal has a trap in it.** When `content/rules.html` is absent the kit holds only `RULES_PLACEHOLDER`, a note saying where to put the file. Reconciling a journal to that would overwrite a world's real rules text with an instruction to supply it, so the caller passes `createOnly`, which creates a page that is missing but never rewrites one that is there. The placeholder's fingerprint is in `SHIPPED_FINGERPRINTS` precisely so the opposite direction works: once the file appears, the repair run recognises the stand-in as the kit's own and replaces it. The rules text itself can no longer be checked at load, since it now differs from world to world — the load-time self-check covers the placeholder and `setupHtml`.

**A page carries two fingerprints, answering two different questions.** `contentFingerprint` is taken from what the document actually ended up holding and answers "has anyone written in this page since the kit wrote it?". `sourceFingerprint` is taken from the text the kit was given and answers "is the page already holding this exact source?". Conflating them was a bug: the server sanitizes what it stores, so for any source the sanitizer rewrites — anything an owner might paste into `content/rules.html` — the sanitized text never equals the text that was sent, and every repair run would rewrite the page and announce it had brought it up to date. Writes stamp `contentFingerprint` with `predictedFingerprint()`, which runs the text through `foundry.utils.cleanHTML` — the same sanitizer — and then `stampFingerprint()` corrects it from the stored content if the prediction was off. Without that correction, owner HTML the sanitizer touches would latch the page as hand-edited the instant the kit wrote it, with no way back. A page from before `sourceFingerprint` existed falls back to comparing content, and is stamped once on the next run.

A rules page carries one flag, `contentFingerprint`, of the text the kit last wrote there. Content that still matches it means the kit was the last to touch the page, so a module update may be written over it; content that does not means someone has been writing in it, and their words win. The fingerprint is taken over text that has been through the browser's own parser, because the server does not store the HTML it is sent: `HTMLField` runs it through parse5 and sanitize-html, which trims it, closes an unclosed tag, writes `<br/>` as `<br>`, gives a `<table><tr>` its `<tbody>` and escapes a bare `&`. Hashing what was sent and comparing it against what was stored would latch the kit's own freshly written page as hand-edited the first time a constant gained any of that — and nothing checking the source text could see it coming, since both sides of that check are the same string. Normalizing both sides through a parser that agrees with the server's on all of the above makes the comparison one between two parsed texts rather than between a source string and a stored one. That is also why the content and its fingerprint go in a single `update()`: written separately, a failure between them latches the page as "edited by hand" for good. The page's name goes in the same update, for the reason `ensureMacro` reconciles a macro's name: pages written before the journal and page names were separated carry the journal's own name and stack a title against the sheet's.

Two cases have no flag to read and are decided by shape instead. A page from before the fingerprints existed is matched against `SHIPPED_FINGERPRINTS` — every version of the text the kit has ever shipped, the current one included — and is only claimed if it holds one of them; **add the new fingerprint whenever the text changes, and never take one away**, or the next release will report a pristine page as hand-edited and refuse to update any world that took the last one. And a page carrying no flag is found first by that list and then, failing it, by the name the kit gave it — the one it uses now, or the journal's own, which is what it used before the two were separated. Text is no help for the page that most needs finding, the one a GM has written in; the name finds it, so their words are reported and kept instead of going unrecognised with a second copy of the reference text added beside them. Nothing else is claimed: a page they deleted and replaced under a name of their own is not the kit's to judge, and their journal gets the kit's page back beside it. A journal with no page of the kit's at all has one put back beside whatever else is there, since `createEmbeddedDocuments` adds rather than replaces; the workbook is the exception, and only gets one when the journal is empty, because pages there the kit cannot account for are the table's writing rather than a gap. What `reconcile` actually decides is narrower than it sounds. Text the kit can prove is still its own — flagged, or holding a version it shipped — is brought forward in *both* journals, workbook included: a pristine legacy workbook page has nothing of the table's on it, and leaving it behind would keep the `<h1>` that stacks a third heading under the sheet's title. The flag decides what happens to everything else: in the rules journal an unvouched-for page is reported as edited and a missing one is added beside foreign pages, while in the workbook it is quietly kept and nothing is added to a journal that has pages of its own — being written in is what a workbook is for. For the same reason a refused reconcile leaves the document counted as installed — a macro rename, a deck's ownership, a page that could not be brought up to date: it is there and it works, and marking the world incomplete would prompt the GM to install the kit on every load. A refused deck ownership does get a notification of its own, though: unlike the others, the table runs straight into it, because the players cannot draw from the deck.

An editor round-trip counts as an edit. ProseMirror re-serializes as it saves, so a GM who opens the page and saves without typing changes the fingerprint and the page is left alone from then on. That is the safe direction to be wrong in — the module cannot tell a re-save from a rewrite — and it is why the warning offers deleting the *page* rather than the journal. A vetoed write is not an error: `Document#update` drops the document from the batch and resolves with nothing at all, so every reconcile goes through `applyUpdate()` and tests what came back — checking only for a throw is how a refusal ends up on screen as "the rules journal was brought up to date". Every step of `installKit()` is wrapped in `ensurePart()` for the same reason the deck loop always was — one rejected write used to take the scene, the macros, the completion flag and the summary dialog with it, and the install prompt's callback neither awaits nor catches, so the GM saw nothing at all.

**GM-only writes, with one exception.** Players cannot write world-scoped settings, so every mutating action returns early for non-GMs and the template disables their controls. Contempt is the exception: the rules make taking it the player's own move, so `adjustContempt()` relays a non-GM click to a GM client through **socketlib**, which performs the write there. Any player may adjust any row — the rows are a shared table-facing signal and this is a trust-based game. Everything else stays read-only for players.

**`"socket": true` needs a world relaunch.** socketlib's `registerModule()` refuses a module whose manifest does not declare `socket`, and Foundry reads that field when the **world is launched** — restarting the browser, or even the whole client, changes nothing. Symptom: `socketlib.modules` is empty, `registerModule()` logs to the console and returns `undefined`, and the play surface falls back to GM-only Contempt. Patching `game.modules.get(MODULE_ID).socket = true` at runtime makes registration succeed on that client but the server still drops the relayed event, so it is not a way to test this without the relaunch.

`window.QuietYearCobalt` is the public surface (`installKit`, `openPlaySurface`, `drawWeek`, `tickProjects`, `resetYear`, and the live `app`). The generated macros call into it, so keep those names stable.

**The sidebar tab.** `QuietYearSidebarTab` is an ApplicationV2 tab registered by `registerSidebarTab()` from `init` — `CONFIG.ui[MODULE_ID]` supplies the class and `Sidebar.TABS[MODULE_ID]` the icon-strip entry, both of which `Game#initializeUI` reads between `setup` and `ready`. It renders for players as well as the GM and only launches things: the play surface, and the rules journal found by its `key: "rules"` flag. Its `tabName` is `MODULE_ID`, which is also the tab element's id and the `.quiet-year-sidebar` class the stylesheet hangs off.

**Clicks go through the actions map; nothing else can.** `DEFAULT_OPTIONS.actions` is bound once on the window frame and dispatched by `[data-action]`, so a render landing between a click and its write cannot detach the handler and there is nothing to rebind. A button that needs a payload carries it in its own `data-` attributes and the handler reads them off `target` — which is what keeps `recordAction()` taking the week number from the button that was on screen rather than resolving it when the queued write runs. Everything that is not a click — the `input` listeners that mark a field dirty, the blur/Enter commits, the caret an add button asks for — is bound in `_onRender`, which runs again after every render because the part element it binds to is replaced each time.

**The GM's out-of-band controls live in the window header, not the panel.** `_getHeaderControls()` puts Undo, Undo <the week's last action> and Reset Year in the `⋮` menu: neither belongs to the weekly loop the panel is for, and a player gets no entry rather than a disabled control. The menu is rebuilt every time it opens, which is what lets the Undo entry name what it will take back; it is absent rather than disabled when the stack is empty, because a context menu has no disabled state. A menu entry dispatches through the same `actions` map as a button, but hands the handler the `<li>` that was clicked rather than a button carrying a payload — so only a handler that ignores its second argument can be reached that way. That is why `undoLastAction()` takes no index and pops the week's most recent action: the last one recorded is the one anybody wants back, and there is nothing to carry an index on. Tick Projects stays on the surface: it is step 2 of every week, and it lives in the turn bar.

**The turn bar is the week's spine.** A strip across the top of the panel, above both columns, carries the week and season and — under a rule — the three steps of a turn in the order the rules give them: Draw Card → Adjust Project Dice → Take Action. It replaced a line of prose that named those steps without being able to perform any of them, so the sequence is now the control rather than a caption above one. All three are always present and disable rather than disappear, which is what keeps a player looking at the same shape the GM is — and what lets the bar say where the week has got to: exactly one of them is live at a time. Draw Card until a card is on the table, then Adjust Project Dice, then Take Action, then Draw Card again for the week after. `canDraw`/`canTick`/`canTakeAction` are derived in `_prepareContext` from the state alone, never stored, so every client works the position out for itself and a render from another client cannot leave the bar showing a step that has already been taken. Game over disables all three. It is a grid of `1fr auto 1fr auto 1fr` rather than a flex row so the three come out exactly equal thirds; flexed, the arrows take their share out of one side and leave three different widths. Below `560px` of panel the strip becomes a single column and the arrows go, since an arrow pointing right at a button underneath it is pointing at nothing.

**Step 2 is recorded, not inferred.** Adjusting the dice leaves no other trace in the state — the weeks on a project change, but nothing says whether a tick or the GM's own stepper changed them — so `state.tickedWeek` holds the week whose dice have been adjusted, and `tickProjects()` sets it whether or not any die actually moved. Two things follow. A week with nothing left to count down still has to be walked past, which is the honest reading of the step and keeps the sequence unambiguous; and because that tick is a real move, it pushes an undo entry even when it reduced nothing, so the turn can be walked back. Do not be tempted to infer the step from "no project has weeks left on it": the week's action can *start* a project, which would un-take a step already taken. It is a number rather than a flag on the week's log entry so that undoing a tick restores one scalar and cannot take the week's recorded actions down with it.

**Take Action asks in a dialog.** The third step of the turn opens a `DialogV2.wait` carrying all three choices, a note, and — for a project — its die, rather than spreading them across the strip; that is also what keeps the button identical to the two beside it, with no caret or wrapper of its own. Choosing "Started a project" relabels the note as the project's name and reveals the die, so the action and the project it created are one act rather than two the GM has to remember to pair. Both ways of starting a project — here and the panel's Add Project — go through `startProject()`, which creates it and records the action with the name as its note; the panel's row starts nameless, so its note is empty and the log line is the plain "Started a project". The note records what was known when the action was taken, and naming the project afterwards does not rewrite the year. A button's `callback` return value is what `wait()` resolves to, so the form is read there rather than from a `submit` handler; the dialog carries no cancel button, because the window's own close control already is one — dismissing resolves to `null` rather than rejecting (`rejectClose` defaults to `false` in v14), and that null is the handler's cue to write nothing.

**Adding is a row, not a form.** Every list on the surface — Abundances, Scarcities, Projects, Contempt — ends in one Add button that appends an empty row and puts the caret in it. There is no name box beside the button and no `+` to submit it: the row is where the entry is edited for the rest of the year, so it is where it is written in the first place, and there is one field to learn rather than two that save differently. It follows that **a blank name is a legitimate state**, not an error — `addResource()` defaults to `""`, and neither `renameResource()` nor `renameProject()` warns about an empty field, because an empty field is a row nobody has got to yet. Blank is still not a removal; the trash button is. Project rows added this way start at three weeks and are changed with the row's own − and +, which is why the add button has nothing left to ask for. Contempt is the exception that still names its rows, because "Player 3" is a placeholder people actually use.

The caret is handed over by `_pendingFocus`, a selector set synchronously in the click handler and consumed by the next `_onRender`: both lists append, so the last field the selector matches is the new one. It is consumed by whichever render arrives first — a render this add did not cause is near enough the same moment, and an armed selector left lying about would steal the caret later, in the middle of something else. A write that fails clears it for the same reason.

**A week's actions carry notes, and the old shape still loads.** `week.actions` holds `{ kind, note }`, but years logged before notes existed hold plain kind strings. `weekActions()` normalizes on read rather than migrating the setting, the same way `projectStatus()` does, so a year in progress keeps working; `weekActionLabel()` is the one place that decides how the pair reads on the panel and in the year's log. Write the new shape, tolerate the old, and never assume an entry is a string. The week's record is **read** on the panel and **edited** from the header menu. It is a diamond and a line of text per action — no chip, no × — because it is what happened, not a control; the box appears only once the week has an action in it, since the turn bar already says where the week has got to and a panel saying "no action recorded this week" was saying it a second time, in more space. Taking an action back is the menu's `Undo <action>` entry, which names the kind alone (a note can be a sentence) and is absent when the week has no action. It removes the record only — a project the action started stays on the tracker, which is the point: several cards call for a project as part of their own prompt rather than as the week's action.

The week number is read off the button **before** the dialog opens and before anything is awaited, for the reason every queued action has to: the write queue can put a draw in front of the record, and "the current week" by then is the next one. A dialog only widens that gap.

`PARTS.surface` is deliberately **not** a `root` part: a root part's children replace `.window-content`'s, which would drop the `.qyc-panel` wrapper the container queries hang off. As an ordinary part the wrapper is what gets replaced, and `.window-content` — the scroller — is left alone.

**The play surface is two columns.** `templates/play-surface.html` splits into `.qyc-panel-column`s — the week, Current Card and Resources on the left, Projects and Contempt on the right — because Projects is the one section that grows without bound and pushed everything used weekly below the fold. The window opens at 880px for it. Anything in that stylesheet that reacts to width uses a **container query**, never a viewport media query: the surface is a floating window, so its width has nothing to do with the viewport's, and a media query neither fires when the window is dragged narrow nor stays quiet when a wide window sits on a small screen. The two breakpoints are deliberately arithmetic on each other — the panel unsplits at 770px so that a split column is always wider than the 380px at which the grids nested in it stack — and a new one belongs in the same relation, or the layout gets a width where two grids collapse at once. **The lists' controls are quiet.** Every button inside Projects, Resources and Contempt — the row buttons, the week steppers, the Adds — loses its background and border and sits at half opacity, taking them back on hover and focus, because Foundry's default button is a filled box that reads louder than the project or player name beside it. The turn bar's three steps are the exception and stay full-strength: they are the thing the week is operated with.

## Two traps this file has already hit

**Top-level `const` is global.** `scripts/quiet-year.js` is a classic script, so every top-level `const`/`class` goes into the shared global lexical scope. Declaring one whose name matches a non-configurable global that Foundry already defines — `Sidebar`, and most other core class names — is a SyntaxError raised *before the first statement runs*, so the entire module silently fails to load with nothing in the console. Reach through the namespace (`foundry.applications.sidebar.Sidebar`) instead of destructuring core classes into locals.

**Core CSS is layered; ours is not.** Rules like `.tab[data-tab]:not(.active) { display: none }` live in a core `@layer`, and an unlayered module stylesheet outranks every layered rule regardless of specificity. An unconditional `display: flex` on a sidebar tab body would therefore show it underneath every other tab. Scope such rules to `.active` and to `.sidebar-popout .window-content`.

**Never keep a second copy of a journal's text.** The workbook's source is `setupHtml`; the rules page's is `content/rules.html`, which the repository does not carry at all. A Foundry export of the rules journal used to sit at the project root, byte-identical to the text the module already held and carrying world-specific fields — `folder`, a page `_id`, a `_stats` block naming the system and world it came from — so it was removed rather than kept as a copy that could drift, and the history rewrite has since taken it out of the repository altogether. Do not add one back. Editing either source does reach a world that already has the journal: re-running the installer updates the page in place, unless someone has written in it, in which case their version is kept and the run says so.

Both journal constants open straight into content with no `<h1>`. A single-page journal already renders two headings — the sheet's title bar carries the journal name and the page carries its own — so a third in the HTML just stacks up. `ensureJournal` takes the page name separately for the same reason: pass something shorter than the journal name rather than repeating it.

## Rules fidelity

The seasonal decks are drawn from randomly among undrawn cards, which is equivalent to shuffling once and drawing from the top — see the comments in `drawWeek()`. Two card effects are special-cased and should stay that way: the **King of Summer** discards two further Summer cards (two actions that week), and the **King of Winter** ends the game immediately.
